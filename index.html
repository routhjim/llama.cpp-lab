llama.cpp, measured on Strix Halo and two 7900 XTX

Changes to llama.cpp for AMD's Ryzen AI Max+ 395 and two Radeon RX 7900 XTX eGPUs on Vulkan/RADV, each merged through a pull request with a before and after number from this one machine. The negative results are here too.

Three setups: Qwen3.8-Flash-Next, a 180B sparse MoE, on the integrated GPU with an XTX helping; dense Qwen3.8-27B pipelined over both XTX for many concurrent agent streams; and the 27B on one XTX. None of this is in upstream llama.cpp.

Where Flash-Next prefill time goes at ub 256 (before #62): MoE expert matmuls 40%, two skinny f32 hyper-connection products 23% (fixed by #62), dense projections 17%, attention 6%, elementwise 7%, the gated delta-net recurrence only 1.3%. Findings
~205 ms

per decode step when slots in one verify batch draft different lengths. The batch splits into small ubatches. This, not gating itself, is why per-token p_min gating lost every test on this box.

57% / 21%

of a Flash-Next decode step at np1 is the 8-bit dense path and the MoE experts respectively. With several streams the expert union takes over.

0.389 µs

per token of context on top of a 41.53 ms step: Flash-Next decode at np1 is linear in KV length, with no cliffs.

+18.5% → +2.9%

decode from requantizing Flash-Next's 8-bit dense path, measured without a drafter and then in production with the MTP drafter at depth 3. Quality can match UD-Q4_K_XL (perplexity ratio 0.997), but drafter acceptance still drops 2–3 points, only at draft positions 2 and 3. A no-drafter benchmark overstates any requant of a model served with MTP. Write-up.

0.651 → 0.692

live draft acceptance after re-fitting the MTP head to the requantized model it serves. The head was trained against the bf16 weights; 20 minutes of training on the iGPU against C2T8's own top-20 distribution, unrolled over draft depths 1–3, recovers the loss and passes UD's 0.687. Write-up.

Findings
2.3×

aggregate decode on the same 8-stream test in one day: 115 → 185 tok/s from removing host stalls, then 259–269 from retraining the dock links. Draft acceptance stayed 0.85. Write-up.

37 vs 17

Terminal-Bench 2.1 tasks scored by 77.5 minutes (34 passed), against 23 for the same two cards before these changes and 17 for one XTX. Decode per stream 23.7 vs 13.7 tok/s, prefill 434 vs 274 tok/s per request, same pass/fail outcomes.

0.8 GB/s

was every host↔GPU transfer on both TB5 docks: the controller→GPU link inside each dock trained at 2.5 GT/s (Target Link Speed Gen1). Stepping the port's kernel bandwidth-controller cooling device 1→0 retrains it at 16 GT/s. Note.

83%

of the decode threads' time, before #55, went to waiting on fences for transfers: 38% output readback from card 2 (the Vulkan host buffer was pinned for card 1 only), 33% before each cross-card copy, 12% synchronous input uploads.

What didn't work

Measured and recorded so nobody has to run them again.

Build and run

Reproduce it

cmake -B build -DGGML_VULKAN=ON -DGGML_VULKAN_MMV_MAX_COLS=32 -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

MMV_MAX_COLS=32 matters for Flash-Next: the default of 16 puts a decode cliff at verify batches above 16.

# Flash-Next on the iGPU
build/bin/llama-server -m Qwen3.8-Flash-Next-UD-Q4_K_XL-00001-of-00004.gguf \
  -md mtp-Qwen3.8-Flash-Next-Q4DRAFT.gguf --spec-type draft-mtp \
  --spec-draft-n-max 3 --spec-coupled -ngl 99 -ngld 99 -fa on \
  -ctk q8_0 -ctv q8_0 -lm mmap -lzm auto -c 262144 -np 1 --jinja

Always pass -lm mmap for Flash-Next. With auto, one device that lacks mmap turns it off for all of them, and the load then needs the whole file in RAM.

# Qwen3.8-27B pipelined over two 7900 XTX (one endpoint on :8090)
MODEL=Qwen3.8-27B-Q4_K_S.gguf DRAFT=mtp-Qwen3.8-27B-Q4_K_M.gguf TMPL=qwen38.jinja \
  scripts/two-xtx/run-qwen38-2x.sh --reasoning-format deepseek -rea on --reasoning-effort medium

Check the dock links first: cat /sys/bus/pci/devices/*/current_link_speed on the GPU's upstream port should read 16 GT/s. See the dock note.
